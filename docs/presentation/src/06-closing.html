Infrastructure · production

Same topology, one TLS edge, explicit runbook

deploy/compose.prod.yml reuses the backend image, adds Caddy 2.8 and removes host-exposed dev ports.

Edge

Caddy 2.8

Automatic HTTPS certificates, reverse proxy to web and api, HTTP→HTTPS redirect. Only 80/443 are published.

Data

Named volumes + backups

PostgreSQL, Redis and MinIO volumes persist across deploys. The runbook covers pg_dump/restore, volume backup and a tested rollback path.

Deploy

Image-based

SCRAPEFLOW_IMAGE selects the backend tag; migrate runs before API/worker start; rollback is a tag change plus a migration check.

Not started here: the production Caddy topology needs a real domain and DNS. It is committed and documented, but not verified live in this environment.

Developer experience

One command on Linux, macOS and Windows

Four entry points, identical subcommands. The macOS wrapper delegates to the shared Bash runner; Windows has a native PowerShell implementation.

Entry pointPlatformBehaviour
scripts/run.shLinuxShared implementation: start, logs, status, seed, fix-db-password, stop, reset
scripts/run-macos.shmacOSChecks Docker Desktop and Python, then execs the shared runner
scripts/run.ps1WindowsNative PowerShell 5.1+: creates .env and the S3-mock override without Bash, Python or curl
scripts/run.cmdWindows CMDLauncher that runs run.ps1 with -ExecutionPolicy Bypass

What was verified
  • bash -n passes for both Bash scripts, including in a real Bash 3.2 container.
  • The macOS wrapper delegates correctly (run on Linux).
  • PowerShell: syntax, PSScriptAnalyzer (no errors), status, fix-db-password, .env generation (64-char secrets, mode 600, no BOM), fake-Docker start path.
  • .gitattributes keeps shell/YAML LF and Windows launchers CRLF.

Honest limit: native Windows PowerShell 5.1 + Docker Desktop and native macOS execution were not available on this host. They remain UNVERIFIED; the scripts target those environments and the docs say so.

Scope discipline

What is proven, and what is still an assumption

A production claim is only as good as the environment it ran in. This slide is deliberately split.

Verified on this host

evidence
  • Full dev Compose stack: 11 services, PostgreSQL/Redis/S3 mock healthy, migrations exit 0.
  • Real browser scrape through Selenium Grid: screenshot + HTML + JSON artifacts.
  • Artifact download through the API's presigned redirect.
  • JWT signup/login/refresh and the dashboard session.
  • Celery Beat scheduling, reaper, retention and worker metrics on 9101.
  • 322 Python tests, Ruff, format and mypy; 30 Vitest tests, lint, typecheck, production build.
  • Playwright Chromium E2E: 5 passed, 2 skipped.
  • Runner scripts exercised: Bash 3.2 syntax, PowerShell 7.4.6 behaviour.

Not verified here

external dependency
  • Live Stripe checkout/portal — no API keys or test account.
  • Official MinIO image and lifecycle — the pinned tag returned 401; s3mock was used.
  • Production Caddy topology — needs a real domain and DNS.
  • Commercial proxy gateway — no upstream credentials.
  • Real external webhook receiver — HMAC path is unit-tested only.
  • Hosted GitHub Actions — workflow is config-validated, not run on GitHub.
  • Locust capacity numbers — Locust not installed; profile shape tested only.
  • Native Windows / macOS — scripts target them but were not executed there.

Read this as: the application logic, security boundaries and integrations are implemented and tested locally. Anything that needs a paid or external service is clearly flagged — never presented as already working in production.
