# Strix — automated penetration testing

[Strix](https://github.com/usestrix/strix) is an open-source AI pentesting agent:
it runs the application, chains real exploit attempts, and writes findings with
proofs of concept. We use it as an **advisory** security layer on top of the
existing gates (`ruff`, `mypy`, `pytest`, `pip-audit`, ESLint, Vitest,
Playwright). It does not replace any of them.

## Where it runs

| Surface | Trigger | Scope |
| --- | --- | --- |
| GitHub Actions (`.github/workflows/strix.yml`) | manual `workflow_dispatch` | committed source tree, optional diff scope |
| Linux (`scrapeflow/scripts/security-scan.sh`) | developer | committed source tree, or the running API on `:8000` |
| macOS (`scrapeflow/scripts/security-scan-macos.sh`) | developer | same as Linux, after Docker Desktop checks |
| Windows (`scrapeflow/scripts/security-scan.ps1`, `security-scan.cmd`) | developer | same as Linux, PowerShell 5.1+ |

Strix is deliberately **not** part of the pull-request gate. A run needs an LLM
key, costs money per scan, takes minutes, and produces findings that need human
triage. Blocking every PR on an agent would train people to ignore it.

## Required secrets

Add two repository secrets before dispatching the workflow:

| Secret | Example | Notes |
| --- | --- | --- |
| `STRIX_LLM` | `openrouter/z-ai/glm-5.3` | Any supported provider string, see the Strix docs. |
| `LLM_API_KEY` | provider API key | Sent only to the configured provider. |

Without both secrets the workflow does not fail: it prints a warning and skips
the scan, so forks and fresh clones stay green.

## Running it

### From GitHub Actions

1. Actions → **Strix pentest** → *Run workflow*.
2. Pick the depth (`quick` default), scope (`full` for an audit, `diff` for a
   pull request), severity gate, and USD budget cap.
3. Download the `strix-findings-<run-id>` artifact when the job ends.

Exit codes are mapped explicitly: `1` (fatal) fails the job, `2` (findings)
adds a warning annotation and still uploads the report. The agent can edit the
checked-out tree, so a follow-up step records `git status` and `git diff` into
`strix_runs/agent-edits.*`.

To run it weekly instead, uncomment the `schedule:` block in the workflow and
agree on a budget owner first.

### From a workstation

Install once, then use the entry point for your platform.

```bash
uv tool install strix-agent==1.7.0
export STRIX_LLM="openrouter/z-ai/glm-5.3"
export LLM_API_KEY="..."
cd scrapeflow
```

**Linux**

```bash
./scripts/security-scan.sh            # source audit, detached worktree of HEAD
./scripts/security-scan.sh live       # contract + black-box scan of :8000

STRIX_TEST_EMAIL="you@example.com" \
STRIX_TEST_PASSWORD="..." \
./scripts/security-scan.sh live       # grey-box
```

**macOS**

```bash
export PATH="$HOME/.local/bin:$PATH"   # uv tool install location
./scripts/security-scan-macos.sh
./scripts/security-scan-macos.sh live
```

The macOS wrapper verifies Docker Desktop (including its bundled CLI path) and
the daemon before delegating to the shared Linux script, so the scan logic
cannot drift. If Strix is missing it prints the install command.

**Windows (PowerShell 5.1+)**

```powershell
$env:STRIX_LLM = "openrouter/z-ai/glm-5.3"
$env:LLM_API_KEY = "..."
.\scripts\security-scan.ps1
.\scripts\security-scan.ps1 live

# If the execution policy blocks .ps1 files:
.\scripts\security-scan.cmd live
```

The PowerShell runner checks Docker Desktop, the daemon, `git`, the `strix`
executable and the environment, then uses the same worktree and OpenAPI flows as
the shell script. Reports land in `scrapeflow\strix_runs\`; `strix view` opens
them.

**All platforms**

```bash
strix view
```

The source scan checks out `HEAD` into `.run/strix-worktree` because Strix mounts
a local target **read-write**. Your working tree is never the target. Set
`SF_STRIX_KEEP=1` (`$env:SF_STRIX_KEEP = "1"` on Windows) to keep the worktree
afterwards and review what the agent changed.

`live` mode downloads `/openapi.json` first, so the agent tests the 29 declared
routes instead of crawling. Keep `SF_STRIX_BUDGET` (default `10`) and
`SF_STRIX_MODE` (default `quick`) conservative until you know the cost profile.

## Reading the output

Strix writes each run to `strix_runs/<run-name>/`:

- findings with severity, CVSS, and OWASP category
- the proof of concept and reproduction steps
- a final report you can attach to a review

Exit codes: `0` no findings, `1` fatal error, `2` findings at or above the
configured threshold (headless mode).

Treat every finding as a hypothesis until you reproduce it. The output is
generated by a language model driving real tools; it can be wrong, and it can
report an issue that the code already mitigates elsewhere.

## Safety rules

- **Only scan systems you own.** Strix actively exploits what it is pointed at.
  Localhost, the Compose stack, and this repository are in scope. Anything else
  needs written authorization.
- **Do not turn this into a product feature** that lets tenants scan arbitrary
  URLs. That requires domain-ownership verification, an isolated runner, and
  explicit terms first.
- **Expect code and runtime context to leave the machine.** The agent sends
  source and observations to the configured LLM provider. Never point it at an
  environment holding real customer data or production secrets.
- **Cap the spend.** `--max-budget` is enforced by Strix; the workflow defaults
  to `$10` and `300` turns per agent.

## Current status

Verified: `strix-agent==1.7.0` installs with `uv tool`, and its CLI accepts every
flag this integration passes (`--scan-mode`, `--scope-mode`, `--fail-on`,
`--max-budget`, `--max-turns`). The workflow and all three local entry points are
committed and syntax-checked; the shell script's failure paths (missing secrets,
invalid budget, fatal scan exit) and the macOS wrapper's delegation were
exercised with a stub CLI.

Not yet run: an actual pentest. It needs a real LLM key plus the Docker sandbox
image pull. The PowerShell runner has not been executed on a Windows host either
